## ✨ Идея · 07.08.2026 04:48
Нужно исправить автопочинку на уровне BuildGate, потому что после /edit для dotnet-проекта сборка, вероятно, даже не стартует: не определён toolchain, не найден dotnet, либо ошибка окружения считается неремонтируемой. План: 1. Добавить в BuildCheck.cs надёжный поиск dotnet: PATH, DOTNET_ROOT, Program Files/dotnet, where dotnet, dotnet --info, выбор SDK. Если dotnet не найден, формировать отдельную ошибку environment/dotnet_sdk_not_found, писать в reliability.log и подсказывать установку или настройку PATH, но не запускать AI-ремонт кода. 2. В DetectToolchain/CreateContext для папки с csproj/sln и найденным dotnet принудительно устанавливать ProjectType=csharp-dotnet, BuildCmd=dotnet, BuildArgs=build -nologo -v minimal -clp:ErrorsOnly, BuildWorkdir=RootPath, а также явно выбирать единственный csproj/sln. Если проектов несколько, требовать build.json или параметр пути. 3. Расширить build.json: projectType, buildCmd, buildArgs, buildWorkdir, compilerPreference, repairEnabled, repairMaxRounds, allowedPaths, forbiddenPaths. Это даст ручной override для проблемных проектов. 4. Переделать ClassifyError: ошибки CS*, MSB*, NU*, ошибки компиляции и сборки считать CanAutoRepair=true, а отсутствие dotnet, неверный PATH, недоступность SDK, permission denied, missing project file считать CanAutoRepair=false. 5. В FileOps.ApplyValidatedFiles после применения изменений вызывать BuildGate after-edit только если BuildAfterEdit=true, GlobalAutoRepair=true, SuppressPostApply=false и проект распознан. Перед запуском писать в лог: dotnet path, version, command line, working directory, выбранный проект. 6. В RepairLoop.RunWithContext при первой ошибке сначала вызывать диагностику окружения: проверить dotnet, попытаться safe-fix через повторный поиск SDK, пересоздать build.json, предложить пользователю установить dotnet или выбрать SDK. Если ошибка кодовая, отправлять AI хвост вывода dotnet build, список изменённых файлов и требуемый формат патча, затем применять изменения через validator и rollback. 7. Добавить видимый вывод в консоль: почему сборка не запущена, какой компилятор найден, какая команда выполнена, какой exit code, где лежит отчёт. Это устранит ситуацию, когда автопочинка молча не работает. 8. Проверить сценарий: dotnet --version в той же сессии, /doctor, намеренная ошибка CS1002 или missing using, /edit, после применения должен стартовать dotnet build, затем RepairLoop должен сделать раунд ремонта и добиться успешной сборки или явно показать причину отказа.
